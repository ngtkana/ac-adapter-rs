# Rust ライブラリ用 Doc コメント生成スキル

ライブラリの全公開 API（関数・型・メソッド）に日本語 doc コメントを生成します。

## 原則

1. **簡潔性重視**: 仕様が理解できる最小の長さ。無駄な詳細は削除
2. **数式必須**: 可能な限り $...$ で数学表記（例：$O(n \log n)$、$𝔽_P$）
3. **日本語統一**: すべてのドキュメントを日本語で記述
4. **例は仕様検証**: `assert_eq!` で期待値を検証。期待値は仕様から導出

## 入力

- **ライブラリパス**: 例 `libs/fp_fft/src/lib.rs`
- **オプション**: 特定の指示やスタイル指定

## プロセス

### 1. クレートレベルドキュメント

モジュールコメント (`//!`) を lib.rs 上部に配置。

**構成（簡潔版）**:
```rust
//! 一行説明（何をするか、何に使うか）
//!
//! [地の文（見出しなし）。仕組み・正当性・設計意図を自然文で。自明なら省略可]
//!
//! # 仕様
//!
//! [数式・条件を含めた簡潔な説明]
//!
//! # 例
//!
//! ```
//! [手計算可能で仕様を検証する例]
//! ```
//!
//! # 計算量
//!
//! - 関数A: $O(\log n)$
//! - 関数B: $O(n)$
```

**ガイドライン**:
- 説明は 30-50 行程度（本当に必要なことだけ）
- 「何をするのか」を数式で表現
- 1 つの具体例で使用法を示す
- 各公開項目の概要を一行で列挙

**1行目と地の文の役割（重要）**:
- 1行目は端的な要約 1 文。カタログサイト・rustdoc の一覧に出るのでここだけで用途が伝わるようにする
- 1行目の直後、`# 仕様` より前の無見出しの地の文に「なぜ正しいか・どういう仕組みか」を書く。ここはカタログサイトの詳細プレビューにもそのまま表示される
- 見出し（`# 仕様` 以降）は rustdoc でのみ読まれるリファレンス部分。地の文だけでは追いにくいほど複雑なクレート（wavelet_matrix, link_cut_tree など）に限り、任意で `# 解説` 見出しを立ててよい。見出しを空虚な内容で埋めるくらいなら地の文のままにする

**doc(alias)（別名がある場合のみ）**:
- 旧名・英語/日本語の別名・競プロでの通称がある型・関数には `#[doc(alias = "..."）]` を付与し、rustdoc 検索でヒットするようにする（例: `UnionFind` に `#[doc(alias = "DSU")]`）
- 必須ではない。思い出しやすい別名が実際にある場合のみ

**箇条書きの表記統一**:
- 記号は `-`（ハイフン）で統一する（`*` は使わない）
- 項目名と説明の区切りは `: `（コロン）で統一する（em ダッシュ `—` は使わない）
- **`- [`name`]: 説明` の形式は書かない**。Markdown 上「リスト項目内のリンク参照定義」と解釈され、clippy の `doc-nested-refdefs` lint でビルドが失敗する。必ず `- [`name`][]: 説明` のように空の `[]` を挟む

### 2. 関数・メソッド

**標準見出し構成**: `# 仕様` → `# 例` → `# 計算量` → `# Panics`（順序・命名で統一。該当しない見出しは省略）

```rust
/// 一行説明（何をするのか + 数式あれば含める）
///
/// # 仕様
///
/// 必要に応じて数式で: 入力 $x$、出力 $f(x) = ...$
///
/// # 例
///
/// ```
/// let result = my_func(3);
/// assert_eq!(result, 9);  // 仕様: f(3) = 9
/// ```
///
/// # 計算量
///
/// $O(1)$
///
/// # Panics
///
/// `x < 0` のとき panic する。
pub fn my_func(x: i32) -> i32 {
```

**シンプルな関数**:
- 一行説明 + 例のみ（3-5行）。`# 仕様`は自明なら省略可

**複雑な関数**:
- 一行説明
- `# 仕様`: 入力条件・出力結果を数式で表現
- `# 例`: 具体例
- `# 計算量`: あれば記載
- `# Panics`: 前提条件違反（範囲外アクセス等）でpanicする場合のみ、条件を具体的に記載（例: fp_precalc の `n >= len` のとき panic する）

### 3. 構造体・型

```rust
/// 一行説明（何を表すのか）
///
/// 数式または簡潔な説明。
///
/// # 例
/// ```
/// let x = MyType::new();
/// ```
pub struct MyType {
```

### 4. 例の品質

各例は以下を満たす：
- **短い**: 3-10 行
- **実行可能**: 型推論が必要な場合は型を明示
- **検証可能**: `assert_eq!` で期待値を確認
- **期待値は仕様から**: 実装ではなく仕様をテスト

**悪い例**:
```rust
let x = my_func(5);  // 何の検証もない
```

**良い例**:
```rust
let x = my_func(5);
assert_eq!(x, 25);  // 仕様: f(5) = 25
```

## 出力

修正されたソースファイル全体。

**既存ドキュメント対応**:
- 完全削除ではなく改善（明確化、数式追加、簡潔化）
- 既存構造が良ければ保持

## チェックリスト

- [ ] すべてのドキュメント日本語化
- [ ] 説明は最小限の長さ
- [ ] 数式を入れた（可能な限り）
- [ ] 例は短く、assert で検証
- [ ] 例の期待値は仕様から導出
- [ ] 計算量を記載（あれば）
- [ ] 前提条件違反でpanicするメソッドには `# Panics` を記載
- [ ] 1行目は端的な要約、直後の地の文に仕組み・正当性を記載（複雑なクレートのみ任意で `# 解説` 見出し）
- [ ] 覚えやすい別名がある型・関数に `doc(alias)` を付与（該当する場合のみ）
- [ ] 箇条書きは `-` + `: ` で統一し、`- [`name`]: ` ではなく `- [`name`][]: ` にした

## 検証

```bash
cargo test --lib  # ユニットテスト
cargo test --doc  # doctest
cargo doc         # ドキュメント生成確認
```

期待：doctest すべて PASS、doc ビルド成功
